# W10-OP-TRIMS: stable host-automation IDs for per-operation controls (A06)

Status: implemented by W10. Parallel W1 policy text, if any, yields to this spec for this branch.

## Problem

Operation Enable/Depth/Slice live in the scene bank (four scenes x N operations). They are not host
parameters, so a DAW cannot automate them, and a host parameter list that grew one entry per scene
field (4 x N x 3) would tie automation lanes to scene storage and explode as operations are added.

## Design choice: live overlay trims on the sounding scene

Options:

| Option | Verdict |
|---|---|
| Parameters per scene x operation (4 x N x 3 ids) | rejected: 60 ids today, 84 with seven operations; automation would silently target a scene that may not sound; every stored-scene write from the host would bypass undo and locks |
| Parameters that write into the stored scene | rejected: breaks "host parameter IDs unchanged / settings never rewritten", needs the message thread, floods undo |
| One set of N x 3 parameters that overlay the sounding scene | chosen |

The overlay is applied to the effective settings of whichever scene is sounding (after morph, before
placement gating), in the audio thread, from cached atomics. It never edits a stored scene, is not
in scene files, is not on the undo stack, and ignores scene locks (locks protect the scene editor, not
live performance; this matches MIDI-linked `s:` controls which also bypass the host but respect locks,
the only difference being that trims never persist into the scene).

## Parameters (appended to the APVTS layout; never reorder, never reuse)

For operation index `N` in `0 .. operationCount-1`, generated by loop (so every operation added later,
including W2's indices 5 and 6, is covered automatically):

| ID | Type | Range | Default | Meaning |
|---|---|---|---|---|
| `opNEnable` | choice | Scene, Off, On | Scene | Scene = use the scene's Enable; Off forces it off; On forces it on |
| `opNDepth` | float | 0..1 | 1 | multiplies the scene depth (never boosts) |
| `opNSlice` | float | 0.25..4, centre-skewed so 1 is mid-travel | 1 | multiplies the slice length; result clamped to 1/16..4 beats |

IDs: `op0Enable`, `op0Depth`, `op0Slice`, ..., `op5Depth`, `op6Slice`, `op12Depth` (decimal index, no
padding). Version hint 1. Host display names: "<operation>: Enable trim" etc. (`operationTrimName`).
Registration order: operation-major, kind-minor, after the existing last parameter. Ids are pure
functions of (index, kind) in `core/control/OperationTrims`.

### Extensibility rules

- A new operation takes the next index; its three ids appear automatically. Existing ids are never
  renamed, so projects with automation keep working when operations are appended.
- Operations are never removed or reordered (they already have this rule in the scene format).
- The operation display-name table (`operationDisplayName`) lists seven names; indices without a name
  show "Effect N". The names for indices 5 and 6 are "Filter sweep" and "Bit crush" (W2's order); change
  the table, not the ids, if the order differs.

## Default = no effect

- With every trim at default `applyTrims` does nothing; `effectiveSettings()` returns exactly what it
  returned before (same morph path, no extra copy of changed data).
- Values within 1e-4 of the default count as the default, so a host round trip of the normalised value
  cannot change the sound. Non-finite values count as the default.
- Old projects (no trim parameters) restore with defaults; the restore code already resets parameters
  that are absent from the state.

## RT behavior

- Constructor caches `std::atomic<float>*` for the N x 3 parameters in a fixed array sized from
  `operationCount`. `process()` copies them once per block into an `OperationTrims` value and sets
  `trimsActive = !isIdentity(...)`. No allocation, no locks, bounded work (3N loads).
- `effectiveSettings()` applies the overlay only when `trimsActive`.
- Placement `enabledMask` is computed from the trimmed settings, so Force On enables placement for the
  operation; Force Off removes it.
- Audition: the overlay applies to whatever variation index renders, including a previewed scene.

## Interaction with other features

- Morph: trims apply after the blend. Evolution: trims apply after the evolved scene is chosen.
- MIDI learn: the trims are ordinary `p:` targets (`p:op5Depth`), so they are learnable with no change.
- Locks: not consulted. Undo: not involved. Saved scenes: unchanged.
- Visual window: shows the stored/morphed scene (as today); it does not draw the trim. Documented limit.
