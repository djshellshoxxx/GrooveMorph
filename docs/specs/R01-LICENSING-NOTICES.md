## 1. Objective

Every released artifact ships with an accurate third-party notice file and a recorded license decision, so a Beta cannot go out with unknown terms.

## 2. Facts in the repository today

- No `LICENSE` file exists at the repository root. `README.md` states product licensing is outstanding.
- Dependencies in `CMakeLists.txt`: JUCE pinned at tag `8.0.7` through FetchContent (`GIT_REPOSITORY https://github.com/juce-framework/JUCE.git`). The plugin formats are produced by JUCE's wrappers
  (VST3 today, CLAP via W9). The portable core (`src/core`) has no third-party code. Tests use a local `expect` helper, no external framework (verify when listing dependencies).
- `docs/SPECIFICATION.md` "Licensing gate" notes that JUCE terms changed between major versions and that the framework license must be chosen from the entity/revenue/funding situation and the closed/open decision. It cites JUCE 9;
  the pinned code is JUCE 8.0.7, so the terms to review are those that apply to the pinned tag and to any later upgrade.
- GM-QR-012 says "no ... audio export in MVP". N04 (Print to WAV) is a deliberate scope change; the integrator must amend GM-QR-012 when N04 lands (flagged in the W1 report).

## 3. What must be decided (owner), recorded as a decision

Create `docs/coordination/DECISIONS.md` entry "GM-DEC-10 resolved" containing exactly these fields:

| Field | Value to record |
|---|---|
| Product license | Name and SPDX id of the license for GrooveMorph's own source and binaries (or "proprietary, all rights reserved") |
| Framework license path | Which JUCE license applies to the distributed binaries (open-source copyleft path or a commercial/tier path) and the account/entity it is held under |
| Basis | Who the licensee is (individual or entity), why the chosen tier is permitted for the stated revenue/funding, date checked |
| Source disclosure | Whether source must be offered with binaries and where (repository URL, tag per release) |
| VST3 | License of the SDK headers actually bundled in the pinned JUCE tag (read from the files in the pinned checkout, not from memory), and trademark wording required |
| CLAP | License of the CLAP headers and any JUCE-CLAP adapter used (read from their LICENSE files at the pinned revision) |
| Reviewer and date | Who confirmed it, link to the evidence (LICENSE file paths, URLs, screenshot of terms) |

Rule: the decision is made by the owner. This spec only requires that it exists before a Beta is published as a prerelease; until then releases are labeled "internal build, license undecided" and are not announced.

## 4. Required artifacts per release (owner W9 to implement in the packaging workflow)

1. `LICENSE` (the chosen product license text) in the root of the repository and in every distributed archive/installer.
2. `THIRD_PARTY_NOTICES.txt` in every archive, generated by `shared/scripts/gen_third_party_notices.py` (new, W9): one section per component with name, version/tag/commit, SPDX id, copyright line,
   full license text, and project URL. Components for the Beta: JUCE (pinned tag; list the JUCE modules actually linked), VST3 SDK headers (as bundled by JUCE), CLAP headers (and any adapter), the C++
   runtime redistributables if shipped (Windows), and any font or icon shipped. The script reads the pinned checkout (`_deps/juce-src/...` license files) so it cannot drift from the code.
3. In-app notice: an "About / Licenses" entry (Info tab) showing the product name, version (`VERSION` from CMake), license name, and the text of `THIRD_PARTY_NOTICES.txt` (embedded via `juce_add_binary_data`, no network).
4. Trademark text where the format requires it, for example "VST is a registered trademark of Steinberg Media Technologies GmbH", placed in the notices file and the help page; use of vendor logos only if their guidelines are satisfied.
5. A checksum file and a manifest listing: source commit SHA, JUCE tag, build date, compiler, and the SHA-256 of each archive (extends `docs/alpha/BUILD-MANIFEST.md`).
6. A release checklist row "license decision recorded, LICENSE and notices present in every archive" that the release workflow fails without (a CI step that greps archives for both files).
